# 中→英翻译质检：最终方案（完整版）

## 〇、数据前提与本版调整

**你的实际情况**：术语和语料是**提前查好的 JSON，随句对带入，用的时候直接注入**，agent 内部不做任何检索。有些句对带数据，有些不带。

**由此确定的设计总原则**：

> **数据是“增强”不是“依赖”。带数据的句对走强检查，不带的句对自动降级为纯 LLM 判断，两层路径共用同一套流水线，不做分支系统。**

具体调整：
- 删除原方案的 RAG/embedding 检索模块，改为**随句注入（conditional injection）**
- 术语强匹配、参考译法等规则改为**条件启用**：有数据才查，没数据跳过该项（不报错、不提示）
- 全文术语一致性检查**不受影响**——它统计的是“同一文档内同一术语的译法是否一致”，不依赖外部数据，任何情况都可用
- 错误案例库（采纳的建议1）同样做成 JSON 文件，**启动时全量加载、简单规则匹配**（错误类型 + 术语对），不做向量检索，与你的使用习惯一致

## 一、输入数据契约

### 1. 待检文档（每个句对一条）

```json
{
  "pair_id": "S42",
  "source": "在紧急情况下，系统会自动触发熔断机制。",
  "target": "In an emergency, the system will automatically trigger the fusing mechanism.",
  "terms": [                              // ← 可选，有些句对有，有些没有
    {"src": "熔断机制", "std": ["circuit breaker"], "note": "金融/微服务语境"}
  ],
  "references": [                         // ← 可选，语料参考
    {"src": "系统会自动触发熔断机制", "tgt": "the system will automatically trigger the circuit breaker"}
  ]
}
```

### 2. 错误案例库（独立 JSON 文件，由反馈闭环维护，人工确认后才入库）

```json
[
  {"pattern_type": "term_false_positive", "key": ["产能", "capacity"],
   "case": "历史错误：某句将'产能'译为 capacity 被报术语错误，人工驳回——capacity 是正确译法",
   "verdict": "acceptable", "source": "human_review", "date": "2026-08-30"}
]
```

匹配逻辑（纯代码，无检索）：当前句对命中的术语对/疑点关键词 → 按错误类型过滤 → 精确/包含匹配 key → 命中则注入，最多注入 2~3 条。

## 二、总体架构图

```
输入：句对数组（每条可选携带 terms / references JSON）
        │
        ▼
【P 预处理】
 ① 句对齐校验（输入已对齐则只校验数量/合并拆分标记）
 ② 全文术语译法统计（含库外高频名词短语，文档内自统计）
 ③ 长度比等基础特征
 ④ 案例库加载匹配（启动时全量载入，按句对命中案例）
        │
        ▼
【L1 规则引擎层】确定性，零误报
 ├ 数字/日期/单位归一化比对 ──── confirmed
 ├ 术语强匹配【仅 terms 存在时启用】── confirmed / soft(疑似过译)
 ├ 全文术语译法一致性【始终启用】── confirmed
 ├ 未翻译/公式/标签/标点 ──── confirmed
 └ 长度比异常 ───────────── soft（信号，不是错误）
        │
        ├── confirmed ──────────────┐（直接定案）
        │ soft                     │
        ▼                          │
【L2 LLM 粗检层】单模型 × 4 角色（并行）│
  忠实性A / 术语关键词B / 语义细节C / 流畅性D
  条件注入：terms（有则给）/ references（有则给）/
           soft信号 / 命中的案例库few-shot（正例+负例）
        │                          │
        ▼ 疑点池（并集，宁滥勿缺）    │
【L3 LLM 复核层】逐条独立判定        │
  error（必须引用原文+译文证据）      │
  / acceptable / style_warning      │
  条件注入：references（有则给）     │
  / 案例库负例（有则给）             │
        │                          │
        ▼                          ▼
【合并去重 + origin 标签】◄─────────┘
  → 错误报告（confirmed / warning 分区）
        │
        ▼
【反馈闭环】人工审批 → 更新案例库 JSON / 提出术语库增补建议（输出给人）
```

## 三、各环节详解

### P 预处理

| 步骤 | 内容 | 数据依赖 |
|---|---|---|
| P1 对齐校验 | 输入已是句对，只校验：句对数量合理性、标记 1:n / n:1 合并拆分组（跨句漏译要在组内看）；数量异常报 `alignment_suspect` | 无 |
| P2 全文术语译法统计 | 对**有 terms 数据**的术语：统计其实际译法分布；同时对原文中反复出现的库外高频名词做同样统计（库不全的补偿） | 文档自身 |
| P3 基础特征 | 长度比、数字集合、中文字符残留检测的素材 | 无 |
| P4 案例匹配 | 当前句对的术语对/关键词与案例库匹配，命中则准备注入 L2/L3 | 案例库 JSON |

### L1 规则引擎层

| 检查项 | 启用条件 | 判定 |
|---|---|---|
| 数字/日期/单位 | 始终 | 归一化后集合比对，缺失→漏译数字(confirmed)，多出→过译数字(confirmed)，换算错→confirmed |
| 术语强匹配 | **terms 存在** | 原文含术语→译文句内查 std 译法，未找到→confirmed 术语错误；反向多出→soft |
| 全文术语一致性 | **始终** | 同一术语（含库外高频词）全文译法≥2种→confirmed，报出全部位置 |
| 未翻译 | 始终 | 译文残留中文（白名单除外）→confirmed |
| 公式/标签/标点 | 始终 | 符号 diff / 占位符对应 / 配对检查→confirmed |
| 长度比 | 始终 | <0.3 或 >2.5 → **soft**（供 L2 重点核查，本身不算错误） |

**关键点**：terms 不存在的句对，“术语强匹配”整项静默跳过——该句的术语正确性完全交给 L2 角色B 凭语言能力判断，报告不受影响。

### L2 粗检层：多角色 Prompt

**公共模板（条件注入部分用 `{{#if}}` 表示）**：

```
你是中译英翻译质检专家。只针对你负责的维度在译文中寻找疑点。

原则：
1. 粗检环节，宁可多报不可漏报，后续有复核。
2. 只报你负责的维度。
3. "不够地道/可以更好"不算疑点；改变原意、丢失信息、添加原文没有的信息、
   术语/数字/关键词错误才算。
4. 以下是可接受的翻译，不是错误：意译（意思保住即可）、语序调整、主被动转换、
   拆句合句、同义词选择。

【句对 S42】
原文：{{source}}
译文：{{target}}
{{#if terms}}
【命中术语表（必须核查）】
  熔断机制 → circuit breaker
{{/if}}
{{#if references}}
【参考译法（来自历史语料，仅供参考，不作为判错依据）】
  "系统会自动触发熔断机制" → "the system will automatically trigger the circuit breaker"
{{/if}}
{{#if soft_signals}}
【规则层提示】本句长度比 0.31，疑似漏译，请逐信息点核对。
{{/if}}
{{#if matched_cases}}
【历史案例参考（此前人工复核的结论，同类情况照此把握）】
  - [误报教训] "产能"译为 capacity 曾被误报术语错误，人工驳回：capacity 是正确译法。
  - [真实错误] "灰度发布"译为 gray degree release，人工确认错误，应为 canary release。
{{/if}}

输出每条疑点：
{"pair_id":"S42","span_src":"...","span_tgt":"...","type":"mqm类型","reason":"一句话理由"}
无疑点输出 []
```

**四个角色分工**（注入部分相同，职责段不同）：

| 角色 | 职责 | 提示要点 |
|---|---|---|
| A 忠实性 | 错译/漏译/过译/逻辑 | 方法：原文拆信息点清单→逐项找对应；结合长度比 soft 信号 |
| B 术语关键词 | 库内+库外术语、一致性 | **terms 缺失时此角色是术语检查的唯一防线**，prompt 中明确“本句无术语表，凭语言能力判断专业名词译法”；注入全文译法分布 |
| C 语义细节 | 否定/情态/时态/程度/比较 | 给出典型对照（“必须”→must 而非 should；“略有下降”≠dropped significantly） |
| D 流畅性 | 只报影响理解的问题 | 默认怀疑自己，拿不准不报 |

**案例注入规则**：负例（误报教训）+ 正例（真实错误）都收，每句最多 2~3 条；只有**人工确认**的案例才进注入池。

### L3 复核层

逐条独立判定，prompt 核心（与上一版一致，数据部分条件化）：

```
你是翻译质检终审官。独立、严格地判定以下疑点。

【判定规则】
■ 判 error，当且仅当以下任一成立，且能引用原文+译文的具体片段作证据：
  E1 错译 E2 漏译 E3 过译 E4 术语/不一致 E5 数字/单位/公式 E6 逻辑错乱
■ 判 acceptable：意译、语序调整、用词不同但语义正确、表达不够优雅但准确——必须判 acceptable
■ 判 style_warning：语义正确但术语不统一/明显不规范，不是错误，仅提示

【证据要求】判 error 必须给出原文片段+译文片段，两者对照能看出"意思变了"，
做不到一律 acceptable。

{{#if references}}
【参考译法】译文与参考在关键信息（数字/主体/否定）一致→倾向 acceptable；冲突→重新核查。
{{/if}}
{{#if matched_negative_cases}}
【历史误报案例】同类情况曾被人工判定为可接受，请对照把握尺度。
{{/if}}

【输入】原文 / 译文 / 全文术语译法统计 / 待复核疑点
【输出】{"pair_id","verdict":"error|acceptable|style_warning","type",
 "span_src","span_tgt","evidence":{"src","tgt","explanation"},
 "severity":"critical|major|minor","suggestion":"..."}
```

### 合并与 origin 标签（采纳的建议2，升级版）

每条最终输出带结构化来源：

```json
{
  "pair_id": "S42",
  "type": "term_error",
  "severity": "major",
  "origin": {
    "layer": "L1",
    "detail": "term_strong_match",
    "corroborated_by": ["L2:B", "L3"]
  }
}
```

- `layer + detail` 到规则/角色粒度（L1 的 8 条规则、L2 的 4 个角色、L3）
- `corroborated_by` 记录交叉确认：多层同报→高置信，人工可免复核；单源 minor→低优先级队列
- 去重规则：L1 与 L3 撞车保留 L1 版本并记 `also_confirmed_by_L3`；span 重叠>70% 且类型相同合并取最高 severity

### 反馈闭环

| 触发 | 动作 | 落地形式 |
|---|---|---|
| 人工改判（error→acceptable） | 入案例库**负例**，进入 L2/L3 注入池 | 写案例库 JSON（人工点击确认即入库） |
| 人工确认真错误 | 入案例库**正例** | 同上 |
| L1 发现库外术语的主流译法 | 输出**术语库增补建议**（不自动写库） | 报告附录，由你在自己的流程里维护术语 JSON |
| 无错误的高质量句对 | 输出**语料候选** | 同上 |

案例库由本 agent 维护（人工审批后写入），术语/语料 JSON 仍由你原有的流程产出——**agent 只消费术语/语料，只生产案例和建议**，职责边界清晰。

## 四、错误判定总表

| 来源 | 判定 | 进最终错误列表 |
|---|---|---|
| L1 机械规则（数字/公式/标签/未翻译/标点） | confirmed | ✅ |
| L1 术语强匹配（terms 存在时） | confirmed | ✅ |
| L1 全文术语一致性 | confirmed | ✅ |
| L1 长度比等软信号 | soft | ❌ 仅注入 L2/L3 |
| L2 疑点 + L3 判 error（有证据） | confirmed | ✅ |
| L2 疑点 + L3 判 acceptable | rejected | ❌（计入驳回率统计） |
| L2 疑点 + L3 判 style_warning | warning | ⚠️ 单独区域，“不是错误” |

## 五、监控指标与调优

| 指标 | 算法 | 调优动作 |
|---|---|---|
| 检出率 | Golden Set 已知错误被报出比例，分错误类型 | 短板类型→加 L2 角色/L1 规则 |
| 误报率 | 人工改判 acceptable ÷ 报告错误数，**按 origin.layer/detail 分别统计** | L1 高→修规则或术语；L2 某角色高→收紧；L3 放走真错→案例库补正例 |
| L3 驳回率 | acceptable ÷ 疑点总数 | >90% 的角色收紧或下线；过低→L2 保守，可能漏检 |
| 数据增益 | 有/无 terms 的句对错误检出率对比 | 量化术语数据价值，指导术语库补全方向 |

## 六、实施顺序

1. **第 1 步**：输入解析（含条件字段容错）+ L1 全部规则（术语强匹配按 terms 有无条件启用）+ 现有单模型质检作为角色 A，输出即带 origin 标签（零成本，第一天就有）
2. **第 2 步**：加 L3 复核，接入 references / 案例负例条件注入
3. **第 3 步**：L2 补齐 B/C/D 角色；建立案例库 JSON 与人工审批入口
4. **第 4 步**：Golden Set 100~300 句对，上线指标看板，进入反馈迭代
