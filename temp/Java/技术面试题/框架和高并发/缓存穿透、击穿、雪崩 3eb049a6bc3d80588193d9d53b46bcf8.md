# 缓存穿透、击穿、雪崩

## 缓存穿透、击穿、雪崩 & 解决方案

这三个问题名字很像，但**场景和解法完全不同**，一张表先建立直觉：

| 问题 | 一句话 | 目标 key | 影响范围 |
| --- | --- | --- | --- |
| **穿透** | 查一个**根本不存在**的数据，缓存挡不住，每次都打到 DB | 不存在的 key | 单个恶意请求 |
| **击穿** | 一个**热点 key 刚好过期**，瞬间大量请求打 DB | 存在但刚过期的热 key | 单个热点 key |
| **雪崩** | **大量 key 同时过期**，或 Redis 挂了 | 一大批 key | 整个 DB |

---

## 一、缓存穿透（Penetration）

### 是什么？

请求查询一个**缓存和 DB 里都没有的数据**。因为缓存里没有，每次请求都会穿透到数据库。

```
请求查 user id = -1 / 999999999
  → Redis 没有（因为根本不存在）
  → 打到 MySQL
  → MySQL 也没有
  → 返回空
  → 下一个请求重复以上流程
```

**危害**：恶意攻击时，DB 被大量无效请求打满。

### 解决方案

#### 方案 1：缓存空值（最简单）

数据库查不到也写进缓存，设短 TTL：

```
User user = redis.get("user:" + id);
if (user == null) {
    user = userMapper.selectById(id);
    if (user == null) {
        redis.set("user:" + id, "", 60, TimeUnit.SECONDS);  // 缓存空值 60s
        return null;
    }
    redis.set("user:" + id, user, 30, TimeUnit.MINUTES);
}
return user;
```

**缺点**：空值多了占内存，且可能短时间内数据真的写进来了但缓存还是空（可接受，60s 后自动过期）。

#### 方案 2：布隆过滤器（推荐，前面 Redis 那节讲过）

在缓存前面加一层布隆过滤器，**不存在的 key 直接拦截，连 Redis 都不查**：

```
请求 → 布隆过滤器判断"这个 ID 可能存在吗？"
        ↓ 不存在（100% 准确）
      直接返回，不查 Redis、不查 DB
        ↓ 可能存在
      查 Redis → 查 DB
```

适合：系统上线时把所有合法 ID 预加载到布隆过滤器。

#### 方案 3：参数校验

接口层直接拦截非法请求（`id <= 0` 直接拒绝），挡掉最简单的攻击。

## 二、缓存击穿（Breakdown）

### 是什么？

**一个热点 key**（被超高并发访问）在某个时刻刚好过期，瞬间成千上万请求同时打到数据库。

```
热点商品 key = "goods:1001" 过期了
  → 线程 A 来查，Redis 没有
  → 线程 B 来查，Redis 没有
  → 线程 C、D、E... 同时打到 MySQL
  → DB 瞬间被压垮
```

**和穿透的区别**：数据**是存在的**，只是刚好这一刻缓存过期了。

### 解决方案

#### 方案 1：互斥锁（推荐）

只让**一个线程**去重建缓存，其他线程等待后读缓存：

```
public User getUser(Long id) {
    String key = "user:" + id;
    User user = redis.get(key);
    if (user == null) {
        // 尝试拿锁，只让一个线程去查 DB
        String lockKey = "lock:" + key;
        try {
            // SETNX 加锁，超时 10s 防止死锁
            Boolean locked = redis.setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
            if (Boolean.TRUE.equals(locked)) {
                user = userMapper.selectById(id);       // 查 DB
                redis.set(key, user, 30, TimeUnit.MINUTES);  // 重建缓存
            } else {
                Thread.sleep(50);                    // 没抢到锁，等一会再来
                return getUser(id);                  // 递归重试
            }
        } finally {
            redis.del(lockKey);                       // 释放锁
        }
    }
    return user;
}
```

**效果**：缓存过期瞬间，只有一个请求打 DB，其他请求稍等后读缓存。

#### 方案 2：热点 key 永不过期

热点数据（首页推荐、爆款商品）**不设物理 TTL**，后台定时任务异步更新缓存。

```
热点 key 不设过期时间
  → 后台定时任务每 5 分钟刷新一次
  → 用户永远读不到 null
```

#### 方案 3：逻辑过期（不依赖物理 TTL）

缓存值里存一个"逻辑过期时间"，发现逻辑过期时，**异步更新缓存**，当前请求返回旧数据：

```
class CacheData {
    Object data;
    long logicalExpireTime;   // 逻辑过期时间
}

// 发现逻辑过期 → 开一个新线程去更新缓存，当前请求直接返回旧数据
```

适合对一致性要求不高、能容忍短暂旧数据的场景。

## 三、缓存雪崩（Avalanche）

### 是什么？

**大量 key 在同一时刻集体过期**，或者 **Redis 节点宕机**，请求全部涌向数据库。

```
场景 1：批量导入数据时，统一设了 30 分钟过期
        → 30 分钟后几万个 key 同时失效
        → DB 瞬间被打垮

场景 2：Redis 主节点宕机，没配哨兵/集群
        → 所有请求直接打 DB
```

**和击穿的区别**：击穿是**一个**热点 key 过期，雪崩是**一大批** key 同时过期（或 Redis 整体不可用）。

### 解决方案

#### 方案 1：过期时间加随机值（最常用）

不要统一 TTL，在基础时间上加随机偏移：

```
// 错误：统一 30 分钟
redis.set(key, value, 30, TimeUnit.MINUTES);

// 正确：30 分钟 + 0~5 分钟随机
int randomOffset = ThreadLocalRandom.current().nextInt(300); // 0~300 秒
redis.set(key, value, 30 * 60 + randomOffset, TimeUnit.SECONDS);
```

**效果**：key 错开过期时间，不会集中失效。

#### 方案 2：Redis 高可用

- **Redis Sentinel（哨兵）**：主节点挂了自动切换从节点。
- **Redis Cluster**：数据分片，部分节点挂了不影响整体。

```
不要单点 Redis！生产至少 1 主 1 从 + 哨兵
```

#### 方案 3：服务降级 / 兜底

当 Redis 不可用或 DB 扛不住时：

- *本地缓存（Caffeine）**兜底一层。
- **返回默认值 / 静态页**（如商品详情页返回"系统繁忙"缓存页）。
- **限流**（Sentinel）：超过阈值的请求直接拒绝，保护 DB。

```
Redis 挂了 → 查本地 Caffeine → 本地也没有 → 返回默认值/降级页面
```

#### 方案 4：缓存预热

系统启动时，提前把热点数据加载到 Redis，避免上线瞬间大量请求直接打 DB。

## 四、三个问题对比总结

| 问题 | 根因 | 核心解法 |
| --- | --- | --- |
| **穿透** | 查不存在的数据 | 缓存空值 + 布隆过滤器 + 参数校验 |
| **击穿** | 单个热点 key 过期 | 互斥锁重建 / 热点 key 永不过期 / 逻辑过期 |
| **雪崩** | 大量 key 同时过期 或 Redis 挂 | TTL 加随机值 + Redis 高可用 + 降级兜底 + 限流 |

---

## 五、面试一句话回答

> • **穿透**：请求查不存在的数据，缓存挡不住，解法是**缓存空值 + 布隆过滤器**。
• **击穿**：一个热点 key 过期瞬间大量请求打 DB，解法是**互斥锁只让一个线程重建缓存**。
• **雪崩**：大量 key 同时过期或 Redis 挂了，解法是**TTL 加随机值 + Redis 集群高可用 + 降级限流**。
