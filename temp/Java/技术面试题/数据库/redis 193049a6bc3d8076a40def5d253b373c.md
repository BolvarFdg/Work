# redis

## 1. redis 持久化问题

两种持久化方案：RDB，AOF

1. RDB：给数据拍 “全家福”
- **通俗原理**：就像每隔一段时间，给账本里的所有数据拍一张完整照片，保存成一个文件。重启时直接恢复这张 “照片” 里的所有数据。
- **技术细节**：
    - 触发方式：① 手动执行 `save`（阻塞主进程）/`bgsave`（fork 子进程，不阻塞）；② 自动触发（比如配置 `save 900 1`：900 秒内至少 1 次写操作就拍快照）。
    - 存储内容：二进制格式的「数据快照」（只存最终结果，比如 `set name tom` 只存 `name=tom`）。
1. AOF：记「流水账」
- **通俗原理**：不拍照片，而是把每一笔修改数据的操作（比如 `set`/`hset`/`del`）都按顺序记在日志本上。重启时重新执行这些操作，就能恢复数据。
- **技术细节**：
    - 触发方式：实时追加（每执行一个写命令，就往 AOF 文件里加一行）。
    - 同步策略（控制数据安全性和性能）：
        - `always`：每写一条命令就刷到硬盘，数据最安全，但性能最差；
        - `everysec`（默认）：每秒刷一次硬盘，兼顾安全和性能；
        - `no`：交给操作系统决定何时刷盘，性能最好，数据最不安全。

| 对比维度 | RDB（快照） | AOF（日志） |
| --- | --- | --- |
| 存储内容 | 二进制的「数据最终结果」（体积小） | 文本 / 二进制的「写命令」（体积大） |
| 持久化时机 | 定时全量快照（比如 5 分钟一次） | 实时追加（按同步策略刷盘） |
| 数据安全性 | 差：如果宕机，会丢失最后一次快照后的所有数据 | 高：默认每秒刷盘，最多丢 1 秒数据；always 模式几乎不丢 |
| 恢复速度 | 快：直接加载快照文件，无需执行命令 | 慢：要逐条执行日志里的命令 |
| 性能影响 | 低：fork 子进程写快照，主进程几乎无感知 | 中：频繁写日志，`everysec` 模式影响很小 |
| 文件大小 | 小：二进制压缩，占硬盘少 | 大：命令文本，重写后会变小 |
1. 最新版redis使用哪种方式？

最新版 Redis **同时开启 RDB + AOF**（双保险），但有优先级：

- 重启恢复时，**优先用 AOF 恢复**（因为 AOF 数据更全，丢失更少）；
- 如果 AOF 文件损坏 / 不存在，才用 RDB 恢复。
