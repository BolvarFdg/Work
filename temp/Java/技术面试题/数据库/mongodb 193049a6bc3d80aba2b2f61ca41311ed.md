## 1. mongo适合什么场景

### 1. 数据结构多变 / 频繁迭代的场景

- **典型案例**：电商商品、内容管理（文章 / 视频 / 评论）、APP 配置项、用户画像
- **原因**：业务需求迭代快，字段经常新增 / 修改，无需停服改表结构，开发效率提升 50%+。

### 2. 高并发读写 + 大数据量存储

- **典型案例**：社交 APP 动态（朋友圈 / 微博）、实时消息、用户行为日志（埋点数据）、游戏装备 / 道具
- **原因**：单节点可支撑高并发，分片集群可无限扩容，能轻松存储亿级文档，且查询速度快。

### 3. 非结构化 / 半结构化数据存储

- **典型案例**：爬虫数据（网页 HTML/JSON）、日志数据（Nginx / 应用日志）、物联网设备数据（传感器多维度数据）
- **原因**：天然兼容 JSON/BSON，无需转换格式，可直接存储嵌套 / 不规则数据。

### 4. 地理位置相关应用

- **典型案例**：外卖配送（附近的商家）、打车 APP（附近的司机）、社交 APP（附近的人）、地图 POI 检索
- **原因**：原生支持地理空间索引（2d/2dsphere），能高效执行「附近 XXX」「距离 XXX 范围内」等查询，性能远超 MySQL 自定义地理算法。

### 5. 快速原型开发 / 敏捷开发

- **典型案例**：创业项目、MVP 产品、内部工具
- **原因**：不用提前设计表结构，写完代码直接存数据，快速验证业务想法，迭代周期从「天」缩短到「小时」。

### 6. 聚合分析类场景

- **典型案例**：用户行为分析（UV/PV/ 留存率）、运营数据统计、实时报表
- **原因**：聚合管道（Aggregation Pipeline）支持多阶段数据处理（过滤、分组、计算），无需把数据导出到 Hive/Spark，直接在数据库层完成分析。

## 2. 为什么适合大数据量存储？

- 文档模型且支持嵌套，一次io就能拿到所有数据，并且比mysql灵活，不需要一个表里所有行都有同样的字段
- BSON存储数据更加紧凑，体积更小
- 扩容方便

| 维度 | MySQL 横向扩容 | MongoDB 横向扩容 |
| --- | --- | --- |
| 原生支持 | 几乎不支持（需依赖第三方中间件） | 原生支持（分片集群 Sharding） |
| 操作难度 | 极复杂：1. 要手动设计分库分表规则（比如按用户 ID 分）；2. 改代码适配中间件（如 Sharding-JDBC）；3. 手动迁移数据，易出现数据倾斜；4. 扩容后维护成本高 | 极简单：1. 新增服务器节点；2. 集群自动把数据分到新节点；3. 客户端无感知，不用改代码；4. 内置均衡器，自动平衡数据 |
| 扩容上限 | 受中间件 / 分表规则限制，一般最多扩到几十台节点 | 线性扩容，支持数百台节点，几乎无上限 |
| 典型场景 | 中小数据量（千万级），扩容频率低 | 大数据量（亿级 / PB 级），需频繁扩容 |
