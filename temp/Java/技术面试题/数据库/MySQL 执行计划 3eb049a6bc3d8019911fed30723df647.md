# MySQL 执行计划

## MySQL EXPLAIN 执行计划

---

### 一、EXPLAIN 是干什么的？

在 SQL 前面加 `EXPLAIN`，MySQL **不真正执行 SQL**，而是输出这条 SQL 的**执行计划**：优化器打算怎么查、用哪个索引、扫多少行。

```
EXPLAIN SELECT * FROM orders WHERE user_id = 1001 AND status = 1;
```

**用途**：

- 看 SQL **有没有用到索引**。
- 看扫描了多少行（rows），是不是全表扫描。
- 看有没有** filesort / temporary table** 这种性能杀手。
- 优化慢查询的第一步就是看 EXPLAIN。

---

### 二、EXPLAIN 输出的 10 个字段

| 字段 | 含义 |
| --- | --- |
| `id` | 查询序号，越大越先执行；相同 id 从上往下执行 |
| `select_type` | 查询类型（简单查询、子查询、联合查询等） |
| `table` | 当前行查的是哪张表 |
| **`type`** | **访问类型（最重要！）**，性能从好到差排序 |
| `possible_keys` | 可能用到的索引 |
| **`key`** | **实际用到的索引**（NULL 表示没用到索引） |
| `key_len` | 索引用了多少字节（判断联合索引用了几个字段） |
| **`rows`** | **预估要扫描的行数**（越小越好） |
| `filtered` | 结果集过滤百分比 |
| **`Extra`** | **额外信息**（Using filesort、Using temporary 等，重要！） |

---

### 三、重点参数逐个讲

#### 1. `type` —— 访问类型（最关键）

性能从好到差：

| type | 含义 | 性能 |
| --- | --- | --- |
| `system` | 表只有一行数据 | 最好 |
| `const` | 主键/唯一索引等值查询，最多匹配一行 | 很快 |
| `eq_ref` | 联表查询时用主键/唯一索引，最多匹配一行 | 很快 |
| `ref` | 普通索引等值查询，可能匹配多行 | 较好 |
| `range` | 索引范围查询（`>`、`<`、`BETWEEN`、`IN`） | 一般 |
| `index` | 扫描整个索引树（比全表扫描好一点，但还是慢） | 差 |
| `ALL` | **全表扫描**，没用到索引 | 最差 |

**生产标准**：

- 至少要达到 **`range`** 级别。
- 出现 `ALL` 必须优化，加索引或改 SQL。
- `index` 也要警惕，看是不是索引覆盖。

#### 2. `key` —— 实际用了哪个索引

- `NULL`：**没用到索引**，必须排查原因。
- 如果 `possible_keys` 有值但 `key` 是 NULL，说明优化器认为全表扫比走索引还快（表太小，或索引区分度太低）。
- 如果 `key` 比预期的小，说明联合索引没全用上。

#### 3. `key_len` —— 联合索引用了几个字段

判断联合索引用了几个列：

```
-- 联合索引 idx_user_status(user_id, status, amount)
EXPLAIN SELECT * FROM orders WHERE user_id = 1001 AND status = 1;
```

- `user_id` 是 BIGINT（8 字节）→ key_len=8。
- 加上 `status`（INT，4 字节）→ key_len=12。
- 加上 `amount` → key_len 更大。

**key_len 越小，说明索引用得越少**（没用到后面的列）。这就是**最左前缀原则**的验证手段。

#### 4. `rows` —— 扫描行数

- 预估要扫描的行数，**越小越好**。
- `rows=100` 但表有 100 万行，说明索引有效。
- `rows=1000000` 基本等于全表扫描。

#### 5. `Extra` —— 额外信息（重点看）

| Extra | 含义 | 好坏 |
| --- | --- | --- |
| `Using index` | **覆盖索引**，不用回表，性能好 | ✅ 好 |
| `Using where` | 服务器层过滤存储引擎返回的行 | 一般 |
| `Using index condition` | 索引下推（ICP），5.6+ 优化 | ✅ 较好 |
| **`Using filesort`** | **额外排序**（没用到索引排序） | ⚠️ 要优化 |
| **`Using temporary`** | **用了临时表**（GROUP BY / DISTINCT） | ⚠️ 要优化 |
| `Using join buffer` | 联表没用到索引，用了缓冲 | ⚠️ 差 |
| `Impossible WHERE` | WHERE 条件恒假 | 注意逻辑问题 |

**必须优化的两个危险信号**：

- **`Using filesort`**：ORDER BY 没走索引，数据量大时极慢。
- **`Using temporary`**：GROUP BY 用了临时表，数据量大时极慢。

### 四、实战例子

```
-- 慢查询：
EXPLAIN SELECT * FROM orders
WHERE user_id = 1001
ORDER BY create_time DESC
LIMIT 10;
```

假设没建索引，输出可能是：

```
type: ALL
key: NULL
rows: 1000000
Extra: Using where; Using filesort
```

**问题**：全表扫描 + 文件排序。

**优化**：建联合索引 `(user_id, create_time)`：

```
CREATE INDEX idx_user_createtime ON orders(user_id, create_time);
```

再看 EXPLAIN：

```
type: ref
key: idx_user_createtime
rows: 50
Extra: Using where
```

变成了 `ref`，扫 50 行，没有 filesort，搞定。

### 五、面试必答：看 EXPLAIN 重点看哪几个？

按优先级：

1. **`type`**：是不是 `ALL`（全表扫）？至少要 `range` 以上。
2. **`key`**：有没有用到索引？是不是 NULL？
3. **`rows`**：扫了多少行？是不是接近全表？
4. **`Extra`**：有没有 `Using filesort` 和 `Using temporary`？

> **一句话**：type 不能是 ALL，key 不能是 NULL，rows 要小，Extra 不能有 filesort/temporary。
>

### 六、补充：EXPLAIN 扩展版本

```
-- 详细版（MySQL 5.6+），显示更多信息
EXPLAIN FORMAT=JSON SELECT ...;

-- 真正执行并看耗时（MySQL 8.0+）
EXPLAIN ANALYZE SELECT ...;
```

---

### 一句话总结

> EXPLAIN 用来分析 SQL 执行计划，重点看四个字段：**`type`（访问类型，不能 ALL）、`key`（实际索引，不能 NULL）、`rows`（扫描行数，越小越好）、`Extra`（不能有 Using filesort / Using temporary）**。
