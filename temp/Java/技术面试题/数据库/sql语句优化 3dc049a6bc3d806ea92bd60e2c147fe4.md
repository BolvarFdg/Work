# sql语句优化

SQL优化（面试精简版，后端高频）

一、索引优化（重中之重）

1. 避免索引失效
- 不要在索引列上做运算、函数、类型转换
where YEAR(create_time) = 2026 ❌ 索引失效；改成范围create_time between '2026-01-01' and '2026-12-31' ✅
- 隐式类型转换：where phone = 13800138000（字段varchar，传数字）❌
- 模糊查询 %前缀%：like '%abc' ❌ 不走索引；like 'abc%' ✅
- 不等于 != <> not in、is not null 大概率不走索引
- or 连接的字段，两边都要建索引，否则失效
联合索引：最左前缀原则，建立顺序(a,b,c)，查询必须带上最左a，才能命中；范围查询（> < between）右边的列索引失效。
2. 索引设计原则
- 选择性高的字段放联合索引前面（区分度高，比如手机号>性别）
- 不要建过多索引，索引占用磁盘，增删改会维护索引，拖慢写入
- 覆盖索引：查询字段全部包含在索引里，回表查询，减少IO（explain Extra:Using index）
- 主键尽量自增，避免页分裂；主键不要用大字符串、uuid

二、SQL语句写法优化

1. 尽量不用 select *，只查需要字段，减少网络传输、支持覆盖索引
2. 分页：大偏移量limit 10000,10慢。优化：select id from table limit 10000,1，再join回表
-- 低效
select * from user limit 10000,10;
-- 优化
select * from user inner join (select id from user limit 10000,10) t on [user.id](http://user.id/) = [t.id](http://t.id/);
3. in 不要过大，in数量建议几百以内；大数据量换成join
4. exists vs in：子查询结果大用exists；子查询结果小用in
5. 尽量避免子查询嵌套，优先join；join字段必须建立索引
6. order by / group by：尽量利用索引排序，避免 Using filesort 文件排序
7. 禁止在where条件做函数计算

三、explain执行计划（看这4列）

- type：性能等级 system > const > eq_ref > ref > range > index > ALL，至少到range，杜绝ALL全表扫描
- key：实际使用索引，null=没走索引
- rows：预估扫描行数，越小越好
- Extra

◦ Using index：覆盖索引 ✅

◦ Using filesort：文件排序 ❌

◦ Using temporary：临时表，group by没索引 ❌

◦ Using where：存储引擎返回数据后，mysql服务层过滤

四、表结构优化

1. 字段类型尽量小：能用varchar(32)不用varchar(255)；时间推荐datetime，少用timestamp
2. 避免null，null会影响索引，可默认空字符串/0
3. 大表水平分表、垂直分表；冷热数据分离
4. 尽量不使用外键，外键由应用层保证，降低数据库压力

五、业务层面优化

1. 减少数据库查询次数，批量操作代替循环单条插入（mybatis foreach批量）
2. 合理缓存：Redis缓存热点数据，避免频繁查库
3. 大事务拆分，事务尽量短小，减少锁持有时间，降低锁等待、死锁概率
4. 读写分离：主库写，从库读，分担压力

六、锁相关优化（InnoDB）

- 避免长事务，行锁变表锁
- 查询尽量走索引，走索引才是行锁；不走索引会退化成表锁
- 尽量减少范围更新，防止间隙锁

面试高频追问

Q：什么是回表？
二级索引只存索引列+主键，查到主键后，再去主键索引（聚簇索引）读取完整行数据，叫回表；覆盖索引不需要回表。
Q：最左前缀原理？
联合索引(a,b,c)，从左往右匹配，遇到范围查询(> <)，后面索引失效。
Q：limit大分页为什么慢？
MySQL需要扫描并丢弃前面10000行，才取后面10条。
Q：in和exists区别？
in是子查询结果先查出来，主表匹配；exists主表逐行，子查询做匹配判断。
Q：覆盖索引是什么？
查询所有字段都在索引中，不需要回表，Extra为Using index。
一句话背诵

索引遵守最左前缀，规避索引失效；拒绝select，优化分页join；explain看type和extra；缩短事务，减少锁；热点数据加缓存。*
