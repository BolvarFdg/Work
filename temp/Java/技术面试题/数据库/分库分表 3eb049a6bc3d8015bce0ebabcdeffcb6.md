# 分库分表

## MySQL 分库分表

---

### 一、它解决什么问题？

当单库单表撑不住的时候：

| 问题 | 表现 |
| --- | --- |
| **单表数据量太大** | 单表几千万行，索引膨胀，查询变慢 |
| **写 QPS 太高** | 单库写入几千 TPS，磁盘 IO 打满 |
| **单库连接数瓶颈** | MySQL 连接数有上限 |
| **单表维护慢** | 加索引、DDL 锁表时间过长 |
| **单机资源瓶颈** | 磁盘、内存、CPU 到顶 |

> 经验值：单表 **500 万行以内**性能良好；超过 **1000 万**就要考虑分表。
> 

---

### 二、两种拆分方式

#### 1. 垂直拆分（按业务/列拆分）

**垂直分库**：按业务把不同表拆到不同数据库。

```
拆分前：一个 db 里有 user、order、product、pay 所有表
拆分后：
  user_db     → user 表
  order_db    → order 表
  product_db  → product 表
  pay_db      → pay 表
```

**垂直分表**：把一张宽表的列拆到两张表（冷热分离）。

```
原来一张 user 表有 50 个字段：
  → user_base：id, name, phone, email（常用字段）
  → user_ext：id, intro, avatar, settings（大字段/不常用）
```

**优点**：业务解耦，专库专用，简单。
**缺点**：没有解决单表数据量大的问题。

---

#### 2. 水平拆分（按数据行拆分）

把同一张表的数据按规则分散到**多个库或多个表**，每张表结构相同。

```
拆分前：order 表 1 亿行
拆分后：
  order_0：user_id % 16 = 0 的数据
  order_1：user_id % 16 = 1 的数据
  ...
  order_15：user_id % 16 = 15 的数据
```

---

### 三、水平拆分的 4 种路由规则

#### 1. 哈希取模（最常用）

```
-- 按 user_id 哈希后对 16 取模，分到 16 张表
table_index = user_id % 16
```

**优点**：数据分布均匀。
**缺点**：扩容麻烦（从 16 张表扩到 32 张，所有数据要重新取模迁移）。

#### 2. 范围分片

```
-- 按 ID 范围
order_0：id 1 ~ 1000 万
order_1：id 1000 万 ~ 2000 万
order_2：id 2000 万 ~ 3000 万
```

**优点**：扩容简单，加新表就行。
**缺点**：热点问题（最新的数据都打在最新的表上）。

#### 3. 按时间分片

```
-- 按月分表
order_202601
order_202602
order_202603
```

**适用**：日志、订单等时间敏感数据。

#### 4. 一致性哈希

解决普通取模扩容时数据大量迁移的问题，只迁移少量数据。

---

### 四、分库分表带来的 5 个新问题

#### 1. 分布式全局 ID

分表后不能用 `AUTO_INCREMENT`（每张表都会从 1 开始，主键冲突）。

**主流方案**：

| 方案 | 原理 | 优缺点 |
| --- | --- | --- |
| **UUID** | 随机生成 | 简单但太长，索引乱 |
| **Snowflake 雪花算法** | 时间戳 + 机器 ID + 序列号 | 推荐，有序且唯一 |
| **Redis INCR** | 原子自增 | 性能好，依赖 Redis |
| **号段模式** | 一次取一段 ID（如 1~1000） | 主流做法，ShardingSphere 默认 |

```
Snowflake 结构（64 bit）：
  1 bit 符号位 | 41 bit 时间戳 | 10 bit 机器 ID | 12 bit 序列号
```

#### 2. 分布式 JOIN

跨库 JOIN 没法直接做。解法：

- **冗余字段**：把要 JOIN 的字段冗余到两张表。
- **全局表**：字典表（如地区、品类）每个库都放一份。
- **应用层组装**：查两次再内存拼接。

#### 3. 分布式事务

跨库写操作不能用本地事务。解法：

- **最终一致性**：本地消息表 + MQ 异步补偿。
- **Seata**：分布式事务框架（AT 模式）。
- **TCC / Saga**：柔性事务。

#### 4. 跨分片分页/排序

```
-- 这个 SQL 怎么查？
SELECT * FROM order ORDER BY create_time DESC LIMIT 10000, 10;
```

**解法**：

- 每个分片都执行一次，**应用层合并排序**（归并排序）。
- 深度分页很慢，改成**游标分页**（WHERE id > last_id LIMIT 10）。

#### 5. 扩容与数据迁移

从 16 张表扩到 32 张，要重新做数据路由。需要：

- **双写迁移**：新老库同时写，历史数据迁移完切流量。
- **一致性哈希**减少迁移量。

### 五、常用中间件

| 中间件 | 定位 |
| --- | --- |
| **ShardingSphere（Sharding-JDBC）** | JDBC 层增强，Java 应用内嵌，推荐 |
| **MyCat** | 独立代理层，对应用透明 |
| **Vitess** | YouTube 开源，云原生 |
| **TDDL** | 阿里开源 |

**Sharding-JDBC 示例**：

```
shardingRule:
  tables:
    order:
      actualDataNodes: ds_${0..1}.order_${0..15}
      tableStrategy:
        inline:
          shardingColumn: user_id
          algorithmExpression: order_${user_id % 16}
      databaseStrategy:
        inline:
          shardingColumn: user_id
          algorithmExpression: ds_${user_id % 2}
```

### 六、一张图总结

```
分库分表
├── 垂直拆分
│   ├── 垂直分库（按业务拆：user_db / order_db）
│   └── 垂直分表（按列拆：宽表 → 主表 + 扩展表）
└── 水平拆分
    ├── 哈希取模（均匀，扩容麻烦）
    ├── 范围分片（扩容简单，有热点）
    ├── 时间分片（按月/季度）
    └── 一致性哈希（扩容迁移少）

伴随问题：
  全局 ID（Snowflake/号段）
  分布式 JOIN（冗余/全局表/应用组装）
  分布式事务（最终一致/Seata）
  跨分片分页（归并排序/游标）
  扩容迁移（双写）
```

---

### 七、一句话总结

> 分库分表解决单表数据量过大和单库性能瓶颈：**垂直拆分**按业务/列拆库拆表，**水平拆分**按行用哈希/范围/时间规则把数据分散到多表多库；代价是引入全局 ID、分布式事务、跨分片 JOIN 和分页等复杂度，生产用 ShardingSphere 这类中间件屏蔽细节。
>
