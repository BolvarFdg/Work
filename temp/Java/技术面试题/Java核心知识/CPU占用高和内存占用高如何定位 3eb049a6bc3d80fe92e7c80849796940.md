# CPU占用高和内存占用高如何定位

## 线上 CPU 高 / OOM 定位 & 两者区别

---

## 一、CPU 占用高怎么定位？

### 标准流程（5 步）

#### 第 1 步：找到进程

```
top                          # 看哪个 java 进程 CPU 最高，记下 PID
ps -ef | grep java
```

#### 第 2 步：找到是哪个线程在吃 CPU

```
top -Hp <PID>                # 列出该进程下所有线程的 CPU 占用
                             # 记下 CPU 最高的线程 ID TID
```

#### 第 3 步：把线程 ID 转成 16 进制

```
printf "%x\n" <TID>          # 输出如 1a2b
```

> 因为 `jstack` 里的线程 ID 是 16 进制的，必须转换才能对应上。
> 

#### 第 4 步：导出线程栈，定位代码

```
jstack <PID> | grep <16进制TID> -A 30
```

或者用 **Arthas**（推荐，省去上面所有步骤）：

```
# 启动 arthas
java -jar arthas-boot.jar

# 直接列出最忙的 3 个线程
thread -n 3
```

Arthas 会直接打印出哪个线程在执行哪个方法的哪一行。

#### 第 5 步：分析栈顶方法

看到栈里哪段代码在疯狂执行，就是元凶。

---

### CPU 高的常见原因

| 原因 | 典型现象 | 排查点 |
| --- | --- | --- |
| **死循环 / 无限递归** | 某个业务线程 100% CPU | 栈顶是业务代码 |
| **频繁 GC** | GC 线程（VM Thread / GC task）占满 CPU | `jstat -gcutil <pid> 1000` 看 YGC 频率 |
| **正则回溯** | 栈顶是 `Pattern$...` 相关 | 复杂正则匹配大文本 |
| **锁自旋 / 忙等** | `BLOCKED` / `WAITING` 线程多 | `jstack` 看锁竞争 |
| **频繁序列化/加密** | 栈顶是 JSON/加密/压缩 | 大对象频繁转换 |
| **线程数爆炸** | 几百个线程切换上下文 | `jstack | grep "\"" | wc -l` |

### 辅助命令

```
jstat -gcutil <PID> 1000     # 每秒看一次 GC，YGC/FGC 频繁就是内存问题引发的 CPU 高
jstack <PID> > stack.txt      # 多次导出对比，看线程是否一直在跑同一段代码
```

## 二、内存高 / OOM 怎么定位？

### 先看 OOM 是哪一种

| 报错信息 | 含义 |
| --- | --- |
| `java.lang.OutOfMemoryError: Java heap space` | **堆内存**不够 / 内存泄漏 |
| `OutOfMemoryError: Metaspace` | 元空间爆了（类加载太多，动态生成类） |
| `OutOfMemoryError: Direct buffer memory` | **堆外内存**泄漏（Netty/NIO） |
| `OutOfMemoryError: GC overhead limit exceeded` | GC 花了 98% 时间只回收了 2% 内存 |
| `unable to create new native thread` | 线程数太多，不是堆问题 |

### 标准流程（4 步）

#### 第 1 步：启动时加好自动 Dump 参数（必须提前配）

```
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/data/dumps/ \
     -Xms2g -Xmx2g \
     -jar app.jar
```

> OOM 时自动生成 `hprof` 堆转储文件，事后分析。没配这个参数，出了问题只能现场抓。
> 

#### 第 2 步：现场抓堆（服务还活着但内存涨得快）

```
# 方式 1：jmap 抓完整堆
jmap -dump:format=b,file=/data/heap.hprof <PID>

# 方式 2：Arthas 抓
heapdump /data/heap.hprof

# 方式 3：先看对象直方图（快速看哪类对象最多）
jmap -histo <PID> | head -20
```

> `jmap -histo` 不dump整个堆，只看统计，适合线上紧急排查。看 `[C`（char[]）、`[B`（byte[]）、HashMap、业务对象哪个占得最多。
> 

#### 第 3 步：用 MAT 分析堆转储

把 `heap.hprof` 下载到本地，用 **Eclipse MAT**（免费）打开：

1. **Dominator Tree**：按对象大小排序，看谁占内存最多。
2. **Leak Suspects**：MAT 自动分析泄漏嫌疑报告。
3. **Biggest Objects**：最大的几个对象。
4. 看这个大对象被谁引用（**Reference Chain**），找到为什么不被回收。

```
MAT 核心思路：
  谁占内存最大（Dominator）
  → 它被谁引用着（GC Root 引用链）
  → 为什么该释放没释放（是不是 static 集合、ThreadLocal、缓存没清）
```

#### 第 4 步：常见内存泄漏点

| 泄漏点 | 现象 |
| --- | --- |
| **static 集合不断 put** | Map/List 是 static 的，只加不删，只增不减 |
| **ThreadLocal 没 remove** | 线程池线程复用，ThreadLocal 数据越积越多 |
| **连接/流没关** | `InputStream`/`Connection` 没关闭，对象无法回收 |
| **缓存不设过期** | 本地 HashMap 当缓存，数据只写不删 |
| **监听器/注册没反注册** | 注册了但没注销，对象一直被引用 |
| **字符串常量泄漏** | 大量 `String.intern()` |
| **Netty 堆外内存泄漏** | `Direct buffer memory` 报错，PoolArena 没释放 |

## 三、CPU 高和 OOM 定位的本质区别

| 维度 | CPU 高 | 内存高 / OOM |
| --- | --- | --- |
| **问题本质** | 线程**在跑什么代码** | 堆里**存了什么对象** |
| **分析粒度** | 线程级（栈帧） | 对象级（引用链） |
| **核心工具** | `top` + `jstack` + Arthas `thread` | `jmap` + `heap.hprof` + **MAT** |
| **看什么** | 线程栈顶方法 | 对象大小 + GC Root 引用链 |
| **典型元凶** | 死循环、频繁 GC、正则回溯 | static 集合、缓存没清、ThreadLocal 泄漏 |
| **是否需要停服务** | 不用，`jstack` 开销小 | `jmap dump` 会 STW 几秒，建议先备份/切流 |
| **快速命令** | `top -Hp` → `jstack` | `jmap -histo` 先看直方图 |
| **定位耗时** | 几分钟出结果 | dump 文件几个 G，MAT 分析较慢 |

### 一句话区分

> **CPU 高 = 看"哪个线程在跑什么代码"**（栈）；**OOM = 看"哪些对象占了内存、被谁引用着"**（堆）。
> 
> 
> 一个是**动态行为问题**（代码在执行时出的问题），一个是**静态数据问题**（内存里存的东西出了问题）。
>

## 四、一张完整排查命令速查表

```
# ===== CPU 高 =====
top                                # 找进程 PID
top -Hp <PID>                      # 找线程 TID
printf "%x\n" <TID>                # 转 16 进制
jstack <PID> | grep <hex_tid> -A 30
# 或 Arthas
thread -n 3                       # 直接看最忙线程

# ===== 内存高 =====
jstat -gcutil <PID> 1000          # 看 GC 频率和各代占用
jmap -histo <PID> | head -30      # 看对象统计
jmap -dump:format=b,file=heap.hprof <PID>   # 抓堆
# 或 Arthas
heapdump /data/heap.hprof
# 下载 hprof 用 MAT 打开分析

# ===== JVM 启动参数（线上必须配）=====
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/
-XX:+PrintGCDetails -Xloggc:/data/gc.log
```

---

### 五、一句话总结

> CPU 高：`top` 找进程 → `top -Hp` 找线程 → `jstack` 看栈，定位死循环/频繁 GC/正则回溯；
OOM：提前配好 `HeapDumpOnOutOfMemoryError`，现场 `jmap -dump` 抓堆，用 MAT 看 Dominator Tree 和引用链，找 static 集合/ThreadLocal/缓存泄漏；
两者区别：CPU 看**线程栈**（动态执行），内存看**对象堆**（静态存储）。
