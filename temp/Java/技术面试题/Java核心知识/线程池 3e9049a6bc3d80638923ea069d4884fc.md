## 一、创建线程池的两种方式

### 方式一：直接构造 `ThreadPoolExecutor`（官方推荐）

通过 `java.util.concurrent.ThreadPoolExecutor` 的构造方法手动创建，参数可控，是《阿里巴巴 Java 开发手册》强制推荐的方式。

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2,                      // corePoolSize
    4,                      // maximumPoolSize
    60L,                    // keepAliveTime
    TimeUnit.SECONDS,       // unit
    new ArrayBlockingQueue<>(10), // workQueue
    new ThreadFactoryBuilder().setNameFormat("demo-pool-%d").build(), // threadFactory
    new ThreadPoolExecutor.AbortPolicy() // handler
);

// 提交任务
executor.execute(() -> System.out.println("任务执行"));

// 关闭线程池
executor.shutdown();
```

### 方式二：通过 `Executors` 工厂类快速创建

`Executors` 提供了几种预置线程池，但**生产环境不推荐**（详见后文）。

| 工厂方法 | 核心特点 | 适用场景 |
| --- | --- | --- |
| `Executors.newFixedThreadPool(n)` | 固定线程数，无界队列 | 负载可控的常规并发任务 |
| `Executors.newCachedThreadPool()` | 核心 0，最大无限，60s 回收 | 大量短时任务 |
| `Executors.newSingleThreadExecutor()` | 单线程，无界队列 | 需要顺序执行的任务 |
| `Executors.newScheduledThreadPool(n)` | 支持定时 / 周期执行 | 定时任务 |
| `Executors.newWorkStealingPool()` | 工作窃取（ForkJoinPool） | CPU 密集型并行计算 |

## 二、线程池的七大核心参数

`ThreadPoolExecutor` 最完整构造方法有 **7 个参数**：

```java
public ThreadPoolExecutor(
    int corePoolSize,
    int maximumPoolSize,
    long keepAliveTime,
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,
    ThreadFactory threadFactory,
    RejectedExecutionHandler handler
)
```

### 1. `corePoolSize` —— 核心线程数

- 线程池长期维持的线程数量。
- 默认情况下，核心线程会**一直存活**（即使空闲）。
- 可通过 `allowCoreThreadTimeOut(true)` 让核心线程也参与超时回收。
- 提交任务时，如果当前线程数 < corePoolSize，即使有空闲核心线程，也会**新建**核心线程来执行新任务。

### 2. `maximumPoolSize` —— 最大线程数

- 线程池允许创建的**最大线程总数**。
- 当核心线程都在忙、队列也满了之后，才会创建非核心线程（救急线程），直到总数达到 `maximumPoolSize`。
- 注意：`maximumPoolSize` 必须 ≥ `corePoolSize`，否则抛异常。

### 3. `keepAliveTime` —— 空闲线程存活时间

- 当线程数超过 `corePoolSize` 时，**超出部分的空闲线程**的最大存活时间。
- 超过该时间仍未被使用，非核心线程会被回收。
- 设置 `allowCoreThreadTimeOut(true)` 后，核心线程也受此参数约束。

### 4. `unit` —— 时间单位

- `keepAliveTime` 的时间单位，取值于 `java.util.concurrent.TimeUnit`：
    - `NANOSECONDS` / `MICROSECONDS` / `MILLISECONDS` / `SECONDS` / `MINUTES` / `HOURS` / `DAYS`

### 5. `workQueue` —— 工作队列（阻塞队列）

- 存放等待执行任务的阻塞队列。常见选择：

| 队列实现 | 特点 | 风险 |
| --- | --- | --- |
| `ArrayBlockingQueue` | 有界数组队列，按 FIFO | 有界，可控制流量 |
| `LinkedBlockingQueue` | 可选有界 / 无界（默认`Integer.MAX_VALUE`） | 无界时可能 OOM |
| `SynchronousQueue` | 不存储任务，直接交给线程 | 需配合大 maximumPoolSize |
| `PriorityBlockingQueue` | 带优先级的无界队列 | 优先级反转风险 |
| `DelayedWorkQueue` | 定时任务专用延迟队列 | — |

> `newFixedThreadPool` 和 `newSingleThreadExecutor` 使用的是无界 `LinkedBlockingQueue`，任务堆积会导致 OOM。
> 

### 6. `threadFactory` —— 线程工厂

- 用于创建新线程的工厂对象。
- 主要作用：**自定义线程名、优先级、守护状态、异常处理器**，便于排查问题。
- 推荐使用 Guava 的 `ThreadFactoryBuilder`：

```java
ThreadFactory factory = new ThreadFactoryBuilder()
    .setNameFormat("order-pool-%d")
    .setDaemon(false)
    .setUncaughtExceptionHandler((t, e) ->
        log.error("线程 {} 异常", t.getName(), e))
    .build();
```

### 7. `handler` —— 拒绝策略

- 当**线程数已达 maximumPoolSize 且队列已满**时，对新提交任务的处理策略。
- JDK 内置四种：

| 策略 | 行为 |
| --- | --- |
| `AbortPolicy`（默认） | 直接抛`RejectedExecutionException` |
| `CallerRunsPolicy` | 由提交任务的线程自己执行该任务（降级、反压） |
| `DiscardPolicy` | 静默丢弃新任务，不抛异常 |
| `DiscardOldestPolicy` | 丢弃队列中最老的任务，然后重试提交 |
- 也可以实现 `RejectedExecutionHandler` 接口自定义（如记录日志、落库、告警）。

## 三、任务提交流程（执行顺序）

提交一个任务后，线程池按以下顺序判断：

1. **当前线程数 < corePoolSize** → 新建核心线程执行任务。
2. **当前线程数 ≥ corePoolSize** → 尝试将任务放入 workQueue。
3. **队列未满** → 任务入队等待。
4. **队列已满，且线程数 < maximumPoolSize** → 新建非核心（救急）线程执行任务。
5. **队列已满，且线程数 ≥ maximumPoolSize** → 触发拒绝策略 handler。

> 一句话记忆：**先核心，再队列，再救急，最后拒绝。**

## 四、为什么《阿里手册》禁止使用 `Executors` 创建线程池

| 工厂方法 | 隐患 |
| --- | --- |
| `newFixedThreadPool` | 队列无界，堆积请求可能导致**OOM** |
| `newSingleThreadExecutor` | 队列无界，同样可能**OOM** |
| `newCachedThreadPool` | 最大线程数`Integer.MAX_VALUE`，可能创建**海量线程**导致 OOM |
| `newScheduledThreadPool` | 同上，线程数无界 |

**正确姿势**：手动 `new ThreadPoolExecutor(...)`，明确有界队列和最大线程数，根据压测结果设置参数。

---

## 五、线程池参数设置参考

- **CPU 密集型任务**（加密、计算）：`核心线程数 ≈ CPU 核心数 + 1`
- **IO 密集型任务**（数据库、RPC、文件读写）：`核心线程数 ≈ CPU 核心数 × (1 + 平均等待时间 / 平均计算时间)`，常见经验值为 **CPU 核数的 2 ~ 10 倍**。
- 实际参数必须通过**压测**确定，不要凭感觉。

## 六、常用监控与关闭方法

```java
// 监控
executor.getCorePoolSize();
executor.getActiveCount();
executor.getQueue().size();
executor.getCompletedTaskCount();

// 关闭（优雅）
executor.shutdown();          // 不再接收新任务，等待已提交任务完成
executor.shutdownNow();       // 尝试停止所有正在执行的任务，返回未执行任务列表
```

## 七、最小可运行示例

```java
import java.util.concurrent.*;

public class ThreadPoolDemo {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2, 4, 60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(10),
            Executors.defaultThreadFactory(),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );

        for (int i = 0; i < 20; i++) {
            int taskId = i;
            pool.execute(() -> System.out.printf(
                "线程 %s 执行任务 %d%n",
                Thread.currentThread().getName(), taskId));
        }

        pool.shutdown();
    }
}
```

---

**要点速记**

- 创建：优先 `new ThreadPoolExecutor(...)`，避免 `Executors`。
- 七参数：**核心数、最大数、存活时间、时间单位、队列、线程工厂、拒绝策略**。
- 流程：核心线程 → 入队 → 救急线程 → 拒绝策略。
- 拒绝策略默认 `AbortPolicy`，可按场景选 `CallerRunsPolicy` 做反压。
- 队列要有界，线程名要可读，参数要压测。

# 线程池核心参数如何确定？

这是线程池实战中最关键的选型问题，我按"怎么定、干什么、怎么选"三块说清楚。

---

## 一、核心参数怎么定？

### 1. `corePoolSize` —— 先用公式估算，再压测修正

| 任务类型 | 估算公式 | 经验值 |
| --- | --- | --- |
| **CPU 密集型**（计算、加密、序列化） | `N_cpu + 1` | CPU 核数 +1，通常 4~8 |
| **IO 密集型**（DB、RPC、HTTP、文件） | `N_cpu × (1 + 等待时间/计算时间)` | 常见为 CPU 核数的 **2~10 倍** |
| **混合型** | 拆成两个线程池，分别按上面算 | — |

> 精确公式：`线程数 = N_cpu × U目标 × (1 + W/C)`，其中 `U目标` 是期望 CPU 利用率，`W/C` 是等待时间/计算时间比。
> 
> 
> **但公式只是起点**，生产上必须用压测（JMeter / wrk）跑 QPS、响应时间、CPU 利用率，逐步调大 corePoolSize 直到 TP99 不再下降，那个拐点就是合理值。
> 

### 2. `maximumPoolSize` —— 突发流量的缓冲上限

- 日常流量下 = `corePoolSize`（不希望救急线程频繁创建销毁）。
- 只有当队列容量**故意设小**（比如 100）、需要用临时线程扛突发流量时，才设为 core 的 **2~4 倍**。
- 如果用了无界队列，`maximumPoolSize` **永远不会生效**——这是新手最容易踩的坑。

### 3. `keepAliveTime` —— 非核心线程的空闲回收时间

- 一般设 **30~120 秒**即可，太短会反复创建线程，太长浪费资源。
- CPU 密集型任务设短一点（30s），IO 密集型可设长一点（5min）。
- 核心线程默认不回收，确认要回收再开 `allowCoreThreadTimeOut(true)`。

### 4. `workQueue` 容量 —— 按峰值 QPS 和响应时间算

```
队列容量 ≈ (corePoolSize × 平均任务耗时) × 预期突发倍数
```

举例：corePoolSize=8，平均任务耗时 50ms，可每秒处理 160 个任务；预期突发 2 秒内多来 500 个任务 → 队列容量设 **500~1000** 就够了。**不要设成 `Integer.MAX_VALUE`**。

---

## 二、阻塞队列和拒绝策略是干什么的？

### 阻塞队列（workQueue）—— 任务的"停车场"

- **作用**：当核心线程都在忙时，新任务不直接失败，而是排队等待。
- **本质**：用内存换系统稳定性，把瞬时高峰摊平成平滑流量（**削峰填谷**）。
- 队列满之前，任务不会丢，也不会创建救急线程。

### 拒绝策略（handler）—— 系统过载时的"保险丝"

- **触发时机**：队列满 **且** 线程数已达 `maximumPoolSize`。
- **作用**：决定最后这条新任务是抛异常、丢、让调用方自己跑，还是丢弃老任务。
- 它是线程池自我保护的最后一道防线，避免 OOM 或无限创建线程把整机拖垮。

---

## 三、怎么选？一张表搞定

### 阻塞队列选型

| 队列 | 适用场景 | 不适用 |
| --- | --- | --- |
| **`ArrayBlockingQueue`（有界）** | **默认首选**，CPU/IO 任务通用，容量可控 | 需要优先级时 |
| `LinkedBlockingQueue`（有界） | 队列长度需动态变化时 | 不要用无界构造（`Executors` 就是踩了这个坑） |
| `SynchronousQueue` | 要求**极低延迟**、任务不排队直接 handoff（如 `newCachedThreadPool`），必须配大 maxPool | 流量不可控时（会爆线程） |
| `PriorityBlockingQueue` | 任务有优先级（如 VIP 请求优先） | 普通任务（徒增复杂度） |
| `DelayedWorkQueue` | 定时 / 周期任务 | 普通任务 |

**结论**：90% 的业务场景用 **`new ArrayBlockingQueue<>(1000)`** 就对了。

### 拒绝策略选型

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| **`AbortPolicy`**（默认） | 抛 `RejectedExecutionException` | **需要上游立刻感知失败**，配合重试/降级；大多数线上服务首选 |
| **`CallerRunsPolicy`** | 让提交任务的线程自己执行 | **需要反压**（如消费 MQ），自然降速、不丢任务 |
| `DiscardPolicy` | 静默丢弃 | 监控上报、日志采集等**可丢失**的次要任务 |
| `DiscardOldestPolicy` | 丢队列最老的，重试新任务 | 只关心最新状态（如实时行情推送） |
| **自定义实现** | 记日志 + 告警 + 落库/MQ | **生产环境最常用**——出问题能追溯 |

**选型原则**：

- 能丢的任务（日志、埋点）→ `DiscardPolicy`。
- 不能丢、需要反压的（MQ 消费）→ `CallerRunsPolicy`。
- 关键业务（下单、支付）→ **自定义 handler**：记日志 + 告警 + 兜底降级（写 DB 或发 MQ 补偿），绝不能静默丢。

## 四、一个实战配置示例

```
// 业务场景：订单查询接口，IO 密集型，8 核 CPU
ThreadPoolExecutor orderPool = new ThreadPoolExecutor(
    16,                                 // core: 8核 × 2
    32,                                 // max: core × 2，扛突发
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),     // 有界队列，容量按压测调
    new ThreadFactoryBuilder().setNameFormat("order-query-%d").build(),
    (r, executor) -> {                 // 自定义拒绝策略
        log.error("订单查询线程池已满，任务被拒绝: {}", r);
        Metrics.counter("order.pool.rejected").increment();
        // 降级：直接返回默认空结果，或写补偿表
        throw new RuntimeException("系统繁忙，请稍后重试");
    }
);
```

---

**一句话总结**：核心数按 CPU 核数 × 任务类型经验估，压测定稿；队列选有界 `ArrayBlockingQueue`；拒绝策略看任务能不能丢——关键业务自定义 handler 记日志告警，可丢任务用 Discard，需要反压用 CallerRuns。
