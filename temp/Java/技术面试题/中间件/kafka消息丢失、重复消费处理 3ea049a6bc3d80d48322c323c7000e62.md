# kafka消息丢失、重复消费处理

好，这次先把底层概念和每个参数讲透，再回头串三个问题。

---

## 一、先搞懂 4 个基础概念

### 1. Topic / Partition / Replica

| 概念 | 解释 |  |  |
| --- | --- | --- | --- |
| **Topic** | 消息的类别（类似数据库的表），如 `order_topic` |  |  |
| **Partition** | Topic 的物理分片。一个 Topic 分成多个 Partition 分布在不同 Broker 上，**并行消费的单位就是 Partition**。一个 Partition 在同一时刻只能被同一个 Consumer Group 里的一个 Consumer 消费 |  |  |
| **Replica** | Partition 的副本，分两种：**Leader**（处理所有读写）和 **Follower**（只从 Leader 同步数据，不对外服务）。副本数一般设 3，挂了一个还能顶上 |  |  |

### 2. Offset —— 消息在 Partition 里的"行号"

- 每条消息写入 Partition 时，Kafka 会给它分配一个**单调递增的编号**：`0, 1, 2, 3, ...`
- 这个编号就是 **offset**，它唯一标识这条消息在 Partition 中的位置。
- Consumer 消费消息后，要告诉 Kafka："我已经处理到 offset = 100 了"——这个动作叫**提交 offset**。
- **为什么重要**：
    - Consumer 重启或 Rebalance 后，从"上次提交的 offset"继续消费。
    - 如果**业务处理完了但没提交 offset** → 重启后会重复消费。
    - 如果**消息刚拉到还没处理就提交了 offset** → 宕机后这条消息就丢了。

> 一句话：offset 就是 Consumer 的"书签"，书签翻在哪、翻得对不对，直接决定重复和丢失。
> 

### 3. ISR（In-Sync Replicas）—— 同步中的副本集合

- Leader 会维护一个列表，里面是**跟得上自己进度的 Follower**，叫 ISR。
- Follower 如果落后太多（超过 `replica.lag.time.max.ms`，默认 30 秒），会被**踢出 ISR**。
- `acks=all` 的含义就是：**消息必须写入所有 ISR 副本**才算成功，不是写进所有副本。

### 4. Consumer Group —— 消费者组

- 多个 Consumer 用同一个 `group.id` 组成一个组，共同消费一个 Topic。
- 组内每个 Partition 只被一个 Consumer 消费，所以 **Consumer 数量 > Partition 数量时，多出来的 Consumer 空闲**。
- 不同组之间互不影响，各自维护自己的 offset。

## 二、Producer 端关键参数逐个讲

### `acks` —— 消息写入的"确认级别"

| 取值 | 含义 | 风险 |
| --- | --- | --- |
| `acks=0` | Producer 发出去就不管，不等 Broker 任何回复 | 最快，但消息可能直接丢 |
| `acks=1` | Leader 写入成功就返回 | Leader 挂了、Follower 还没同步到 → 丢 |
| `acks=all`（或 `-1`） | **所有 ISR 副本**都写入成功才返回 | 最安全，延迟略高 |

> 生产环境必须设 `acks=all`。
> 

### `retries` —— 发送失败重试次数

- 发送失败（网络抖动、Leader 切换等）时，Producer 自动重发的次数。
- 默认 `0`（不重试），建议设成 `Integer.MAX_VALUE` 或很大的值。
- **副作用**：如果 Broker 实际已经收到消息，但 Producer 没收到响应，重试就会导致**同一条消息发两次**——这就是重复消费的源头之一。

### `enable.idempotence` —— 幂等生产者（解决 retries 重复）

- Kafka 0.11+ 引入。
- Producer 给每条消息带一个唯一编号（PID + Sequence Number），Broker 发现重复编号就自动丢弃。
- **效果**：重试不再产生重复消息。
- **限制**：只保证**单 Partition、单 Producer 会话内**不重复。跨 Partition、跨 Producer 重启仍然要消费端自己幂等。

### `linger.ms` / `batch.size` —— 攒批发送

- Producer 不是来一条发一条，而是攒一小批再发，提高吞吐量。
- `linger.ms=5`：最多等 5ms 攒一批。
- `batch.size=16384`：一批最大 16KB。
- 这两个参数跟"不丢不重"无关，是性能优化。

## 三、Broker 端关键参数

### `replication.factor` —— 副本数

- 每个 Partition 存几份，一般设 **3**（1 个 Leader + 2 个 Follower）。
- 设 1 等于没副本，Broker 挂了数据就没了。

### `min.insync.replicas` —— 最少同步副本数

- 配合 `acks=all` 使用。意思是：ISR 里至少要有几个副本活着，Leader 才接受写入。
- 一般设 **2**（1 个 Leader + 至少 1 个 Follower 在 ISR）。
- 如果 ISR 只剩 Leader 自己（其他 Follower 都落后被踢出了），Producer 发送会报错——这是**宁可拒写也不丢数据**的保护。

### `unclean.leader.election.enable` —— 脏 Leader 选举

- 当 Leader 挂了，从哪些副本里选新 Leader？
- `false`（推荐）：**只从 ISR 里选**。如果 ISR 全挂了，宁愿不可用也不丢数据。
- `true`：允许从**非 ISR**（落后很多的副本）里选新 Leader。可用性高，但会丢还没同步的消息。

> 生产环境必须 `false`。
> 

---

## 四、Consumer 端关键参数

### `enable.auto.commit` —— 自动提交 offset

- `true`（默认）：Consumer 后台每 5 秒自动提交一次 offset，不管你业务处理完没有。
- **问题**：消息拉下来了，offset 自动提交了，业务代码还在跑，这时进程挂了 → 重启后从已提交的 offset 继续，**这条消息就丢了**。
- `false`：关闭自动提交，**业务处理成功后手动调用 `consumer.commitSync()`** 提交 offset。

### `auto.offset.reset` —— offset 不存在时怎么办

| 取值 | 含义 |
| --- | --- |
| `earliest` | 从 Partition 第一条消息开始重新消费 |
| `latest`（默认） | 只消费新产生的消息，历史消息不要 |
| `none` | 直接抛异常 |

> 新 Consumer Group 第一次连接时，或 offset 过期被删了，就用这个策略决定从哪开始。
>

## 五、重新串一遍三个问题

### 问题 1：重复消费

**怎么产生的？**

1. Producer 设了 `retries`，重试时同一条消息发了两次（没开幂等）。
2. Consumer 处理完业务，还没 `commitSync()`，Rebalance 或进程挂了 → 重启后从旧 offset 重新消费。
3. Consumer 业务代码执行成功了，但写 DB 时超时了，没提交 offset，下次又消费一遍。

**怎么解决？**

- Producer 端：`enable.idempotence=true`（减少 Producer 侧重复）。
- Consumer 端：**业务幂等**——数据库唯一键、Redis `setnx`、状态机校验，重复消费直接忽略。
- 关闭自动提交，业务成功后再手动提交。

### 问题 2：消息丢失

**三个环节都可能丢：**

| 环节 | 怎么丢的 | 怎么堵 |
| --- | --- | --- |
| **Producer** | `acks=0` 或 `acks=1`，Leader 挂了消息没同步到 Follower | `acks=all` + `retries` 大 |
| **Broker** | Leader 挂了，落后的 Follower 当选新 Leader（`unclean.leader.election.enable=true`） | 设 `false` + `replication.factor=3` + `min.insync.replicas=2` |
| **Consumer** | `enable.auto.commit=true`，消息拉到了但没处理完就自动提交了 | 关闭自动提交，业务成功后 `commitSync()` |

**完整不丢配置：**

```
Producer:  acks=all, retries=MAX, enable.idempotence=true
Broker:    replication.factor=3, min.insync.replicas=2,
           unclean.leader.election.enable=false
Consumer:  enable.auto.commit=false, 手动 commitSync()
```

### 问题 3：消息乱序

**怎么产生的？**

- 一个 Topic 有多个 Partition，消息分散在不同 Partition 里并行消费，跨 Partition 天然不保证顺序。
- 即使同一 Partition，Producer 重试时如果没指定 key，消息可能被发到不同 Partition。
- Consumer 端如果用多线程并发处理同一 Partition 的消息，后拉到的消息可能先处理完。

**怎么解决？**

1. **Producer 端**：同一业务实体（如订单 ID）用相同的 key 发送 → Kafka 按 key hash 到固定 Partition → 同一订单的消息一定在同一 Partition，Partition 内**严格有序**。
2. **Consumer 端**：
    - 简单方案：单线程消费每个 Partition。
    - 并发方案：按 key hash 把消息分发到固定线程，同一 key 永远由同一线程处理。
3. **Offset 提交**：必须等前一条消息处理完再提交，不能跳着提交。

> 全局有序（整个 Topic 只有一个 Partition）性能太差，生产一般只做**按业务 key 的局部有序**。
>
